You extract a complete recipe process graph from procedural text.
Return only valid JSON using the schema below.

1. MODEL AND NON-NEGOTIABLE RULE

Every atomic step creates a fresh output snapshot, even if all state
attributes remain unchanged. Different steps never share an output index.
A normal step has one output; a split has a fresh output for each component.
Initial ingredient/context nodes are additional nodes, not action results.

Nodes identify procedural snapshots. Equal attributes do not imply the same
node. Keep the entity name unchanged across snapshots unless a genuinely
new entity is formed. Never consolidate snapshots from different steps.
Every edge connects distinct nodes; the graph must be acyclic.

Examples: wash -> cut -> blanch produces three successive result nodes.
Simmer -> reduce produces two outputs even when both are chunk/cooked.

2. EXTRACT STEPS BEFORE BUILDING THE GRAPH

Resolve entities, references, roles, actions, inputs, receivers and dependencies
from the complete recipe before constructing nodes. Analyze state values to
populate outputs, not to decide whether an output is needed.

One atomic step is one action on one entity or receiving process.
- "Wash, cut and blanch pork": three steps.
- "Cut ginger and add it": cut, then add the resulting ginger.
- Separate additions/layers are separate steps, each with a new receiver.
- For enumerated additions such as "add ginger, scallion and garlic", use
  one addition per ingredient, following explicit order or otherwise mention
  order. This is a deterministic representation convention, not a claim that
  the source required that order. Do not generalize it to inherently joint
  actions such as whisking a mixture or splitting an egg.

Preserve parallel preparation: a serialization order does not imply an edge
between unrelated branches. Do not duplicate a preparation action already
represented elsewhere. A purchased/pre-prepared ingredient may start in its
stated form; do not invent cutting simply because it is described as sliced.
Extract an explicit preparation instruction in the ingredient list if it is
not repeated later. Exclude commentary, quantities and references without
an action. Optional alternatives are not all mandatory steps of one execution;
use the path selected by the supplied recipe context.

3. ENTITY CONTINUITY, PORTIONS AND FLOW CARRIERS

Internally track current nodes per entity/process branch, including portions
when relevant. For each step, read inputs first, allocate fresh output(s),
connect required inputs, then update the relevant current-node records.
Do not mutate an earlier snapshot or reuse consumed ingredients for later
processing. Independent branches remain unchanged.

The same prepared source can supply repeated uses only when the recipe
supports remaining portions. Do not duplicate initial nodes merely for
repeated mentions. If the recipe explicitly splits material, create a fresh
node per output portion/component using split edges. Portions can share the
same canonical name; distinguish them internally and by node index.

Assign roles by function in THIS recipe:
- main: a primary processing branch or structural component, including a
  sauce when the sauce is a substantial independent preparation.
- aux: supporting seasoning, aromatics, oil, sugar, cooking water, etc.
- container: a structurally meaningful cooking-environment snapshot.

Flow-carrier rules:
- In an aux-only cooking environment, container snapshots carry the flow.
- Adding main to that environment creates a new container snapshot receiving
  both the current environment and the main source. Internally remember which
  main entity is now present. If more additions occur before processing, keep
  creating container snapshots, preserving that main identity.
- The next explicit processing action on those contents creates a fresh main
  snapshot. Thereafter, aux additions create fresh main snapshots, not aux or
  container outputs. Do not invent a heat action just to perform this switch.
- Main plus main creates the recipe-supported main/intermediate output.
- Moving to a different heat-processing environment produces a new container
  snapshot for the transfer; subsequent processing produces a new main.
- The same vessel can have successive snapshots. Its name is not its node ID.

Do not create non-heat bowl/plate nodes merely because a vessel is physically
necessary. Assembly can be represented by the assembled food itself.
If the final explicit step is a transfer, its new snapshot represents the
finished food in the destination; do not invent a later processing action or
an extra final node. Use a main output for such a final food transfer.

4. ACTION EDGES AND MULTI-INPUT STEPS

For a single-input action:
old_pork --reduce/heat--> new_pork

For an addition to an existing receiver:
old_receiver --add/prep--> new_receiver
added_source --add/prep--> new_receiver

Both edges belong to ONE atomic step. They are two causal inputs, not two
actions. Use the same supported action/type on both. Within this schema,
edge index identifies a dependency edge; it is NOT an atomic-step ID.
Keep step grouping internally without adding JSON fields.

Every existing receiver must have an edge into the new result; previous
metadata is not a replacement for this edge. Subsequent actions start at
that new result. Thus separate additions produce a receiver chain:
receiver_0 + ginger -> receiver_1
receiver_1 + scallion -> receiver_2

If no receiver exists yet, use the actual contributing inputs to create the
first result; do not invent an empty food/assembly node. Introduce an initial
empty cooking context only when necessary to identify a real heat environment.
Such a context is not a food ingredient and does not imply a second food
branch has merged. Its first add step still creates a fresh receiving node.

Example of an actual branch combination:
current_wok + current_pork --add--> new_wok
new_wok --fry--> new_pork
Preserve BOTH inputs; do not leave the oil/wok preparation disconnected.

Example of finishing:
current_pork --drizzle/prep--> new_pork
honey        --drizzle/prep--> new_pork
This is one drizzle step. A preceding reduce has its own earlier output.

For an explicit split, connect the old source to each new component with
split edges. Multiple outputs here belong to one step. Except for split,
edges into a result belong to that result's single producing step.

5. ASSEMBLY, DISCARD AND COMPLETENESS

Each separate layer creates a fresh assembly snapshot. Keep a common name
such as moussaka and distinguish snapshots by index, not name suffixes.
Never consolidate successive layers because state attributes match.

Every participating input must connect to the result at combination. All
non-discarded branches contributing to the dish must reach the final process.
Do not force unused quantities or genuinely discarded portions into the dish.
If removal/discard is an explicit atomic action, create a new retained-process
snapshot; create an additional discarded-component snapshot only when that
component is represented explicitly. Do not resume from its historical
pre-combination ingredient node. Discard outputs may terminate separately.

Cover the final cooking/finishing operation, not merely preparation or assembly.
Do not invent a step simply to create a more convenient final dish name.

6. ATTRIBUTES AND VOCABULARIES

Determine before/after values from the recipe, but do not manufacture a
value change to justify a node. Unchanged values MUST be copied truthfully.
A heat action does not automatically change chemical_state to cooked;
for example melting can change physical form without cooking.

Ingredient/intermediate physical_state MUST be one of:
solid
chunk
slice
shred
dice
paste
powder
liquid

Do not output pieces or a physical_subtype field.
Use chunk for large cut pieces, slice for thin slices, shred for narrow
strips, dice for small dice. Use solid for an uncut solid ingredient.

Chemical state MUST be raw or cooked.
Node type MUST be main, aux or container.
Container snapshots may omit physical_state and chemical_state, as in the
existing schema. Do not force a food state onto the vessel.
Use container="none" outside a meaningful cooking context; otherwise use
the canonical cooking environment name supported by the recipe.

Flavor is the original inherent characteristic or functional role, NOT
cumulative seasoning history. It MUST be a SINGLE STRING from:
aroma, aromatic, deodorizing, none, salty, savory, sour, spicied, spicy,
sweet, umami.
Never output flavor arrays or propagate added ingredients' flavors into
the receiving entity. For the same entity retain its assigned flavor across
snapshots unless a different recipe-supported entity is formed.

Use lowercase snake_case ingredient names consistently, including in
source_ingredient. Prefer appropriate canonical names:
bay_leaf, beef, cake_base, cake_paste, cassia_bark, chicken_powder, chilli,
cinnamon, cooking_wine, corn_oil, corn_powder, dark_soy_sauce, egg,
egg_white, egg_white_paste, garlic, ginger, honey, lemon_juice,
light_soy_sauce, milk, noodle_sauce, oil, onion, oyster_sauce, pork, powder,
salt, scallion, semi_cake_base, soy_sauce, spice, spice_powder,
spicy_tofu_sauce, star_anise, sugar, threeten_powder, tofu_sauce,
vanilla_extra, vinegar, water, yolk, yolk_paste.
Normalize pork belly to pork and rock sugar to sugar when appropriate.
If no correct canonical term exists, use a concise lowercase snake_case name.
Do not force an incorrect name or number names to distinguish snapshots.

Preferred actions:
add, bake, blanch, cut, drizzle, fry, heat, ice, mold, prepare, reduce,
scrape, sear, shake, simmer, split, stir, wash, whisk.
Map slicing to cut; choose fry/sear from context. Only introduce a different
concise snake_case action if directly supported and no canonical action fits.
Action type MUST be prep, heat or cold.
Examples: cut/add/stir/whisk -> prep; blanch/fry/sear/simmer/bake -> heat;
ice -> cold.

7. INDEXING, PROVENANCE AND VALIDATION

Keep an internal mapping from each atomic step to its inputs and fresh
output(s). Before serialization verify:
- Every extracted step has fresh output(s); different steps have disjoint
  output indices, including steps that leave every attribute unchanged.
- Inputs exist and represent current, causally available snapshots.
- Every existing receiver and added source is connected to the new result.
- All edge endpoints exist, node indices and edge indices are unique,
  no self-loop exists, and topological traversal visits every node.
- Parallel contributing branches converge where the recipe actually combines
  them, and every non-discarded contributing branch reaches the final process.
- Types, names, physical/chemical values and single-string flavors obey the
  vocabularies. No physical_subtype or step_id field has been introduced.

Assign node indices consecutively from 1 in a topological order consistent
with explicit procedural dependencies. Use source mention order to break ties
between independent steps; do not add causal edges to enforce those ties.
Every edge must then have node1 < node2.

Assign consecutive edge indices by producing-step order. Keep each step's
input edges adjacent: existing receiver first, then added sources in mention
order. For split, use component mention order. This ordering is for stable
serialization, not a ranking of causal importance.

Derive previous ONLY after finalizing all edges and indices:
previous[v] = the union of each incoming edge and previous of its source.
Deduplicate by edge_index, then sort by descending edge_index.
An initial node has previous=[]. Each entry copies the final edge's index,
action and type; source_ingredient is exactly its source node's name.
Never include future actions or a disconnected branch's actions. Two input
edges from the same step remain separate provenance entries; do not interpret
them as two chronological actions.

If validation fails, repair topology before output. Do not delete a recipe
action to hide a cycle; give its before/after snapshots distinct indices.

8. JSON SCHEMA AND OUTPUT

Use the existing top-level fields only:
{"nodes": [...], "edges": [...], "recipe_id": "..."}

Ingredient/intermediate node fields:
index (integer), container (string), name (string), type (main or aux),
physical_state (string), chemical_state (string), flavor (single string),
previous (array).

Container node fields:
index, container, name, type="container", flavor="none", previous.
Container and name identify the cooking environment. Physical and chemical
state fields may be omitted for container nodes.

Edge fields:
index (integer), action (string), type (prep/heat/cold),
node1 (source index), node2 (result index).

Previous-entry fields:
edge_index (integer), action (string), type (string), source_ingredient (string).

Do not output internal step grouping, portion IDs, branch labels, subtype
fields, reasoning or validation reports. Return ONLY valid JSON, without
markdown fences or comments.
